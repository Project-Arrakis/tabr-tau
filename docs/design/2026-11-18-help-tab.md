# The Help tab and the end of standing explanations (#980, #981, #985, #973)

Decision of 2026-11-18. The Command Center said too much, all the time: legends, captions, disclosures and notes under every panel. A permanent line has to earn its place. What stays on the page is the state of a control, a result, an error, and the one thing that can hurt at the point where it can hurt. Everything that explains goes to a Help tab.

## Where the Help lives

- **In the repository** as Markdown: `docs/help/*.md`, one page per feature plus a status table of what is checked in the game. GitHub shows the same files.
- **In the program**: the pages are embedded with `go:embed` (package `docs/help`, file `help.go`) and answered by one route, `GET /api/help`, which reads nothing from the save and takes no input. The Help works offline and always matches the running build.
- **In the page**: a new tab, Help (`helpView` in `app.js`), draws the pages with `static/help.js`. It is a small Markdown reader that builds elements with `createElement` and `textContent` only: no raw HTML of a page is ever used, nothing goes to `innerHTML`, and a "<" in a page is a "<" on the screen. It reads headings, paragraphs, lists, tables, bold, code and links. A link to another Help page becomes a button that opens that page inside the editor. Any other link is shown as its text, so a page cannot send the person anywhere. No new dependency.
- **Also on GitHub**: a small link under the page, built from the repository address the server sends (checked against the project's address before it is drawn). It is the only thing in the tab that needs a network; the tab itself never makes a request except the one to its own `/api/help`.
- The public-text check applies to `docs/help` like any other tracked file. A test keeps the pages plain (no HTML, no address, links only to other pages, every file of the folder embedded).

## Structure of the tab

A row of page buttons (Contents, then the pages in the order the index lists them), the page, and the GitHub link. The last page read is remembered in the browser's storage.

## The term clock (#981)

One row, ENDS IN, in hours and minutes: `ENDS IN 18 h 37 m`. Under an hour `37 m`, under a minute `less than a minute`, at or past the end `ended`, unreadable `not known`. A tooltip on the value says: Counts down only while the game is running; as of the last save. The value is the term's end on the play clock minus where the play clock stood when the save was written, both already read by the page (`lbEndsIn` in `app.js`); no new save read. The start, the play-clock seconds, the length of the term and the real time of the save are no longer shown anywhere (the raw numbers stay in the data layer). The decree elected during a term takes effect in the next one, so it is labelled Next term's decree (none yet before the vote), in the section, in the pool tags and in the classic list.

## What stays, on purpose

- Every confirm question, refusal and error message, and every result toast.
- The hints that belong to one control and say what it does or why it is off (tooltips, the line beside a disabled button, the line about a draft decree that is not applied yet).
- State lines: no Landsraad term in this save, no tiers in the save, the board could not be checked, a track the save does not tie to a path.
- Short labels: favor won ≠ earned ≠ collected, any faction can be chosen, the key to the board.
- The per-row grant caption of the classic list, which says what that row's buttons grant (it is the point of the action).

Nothing here is checked in the game.
