### Added

- **Tests of the write path** (#262, audit findings QA-2, QA-4, QA-15): the answer of an attempt to write now has a test for each way it can end without a write (the edits cannot be put back, the queue is held with the conflict named, the game saved while the file was being written, the write failed, the save is read-only) and for the warning of a file that was written but could not be read back; a cascading delete (a bag and what it holds) is tested through the journal, at start and after the game saved; the journal's two size limits are tested; the flush route and the write after every edit request have tests of their own. No change in behaviour.
- CI is steadier against runner flakes (#269): the PSScriptAnalyzer install is tried three times, and the Windows tests have 20 minutes (the job 30) after a runner with a slow disk took over twelve and failed a main run.- **Edits are written as they are made** (#238): there is no Review & save step. While the file cannot be written (the game is in a single-player session, the save's location is not confirmed) the edits are queued in the journal and written by themselves, a few seconds after the file can be, onto the game's newer file when it saved meanwhile. The header shows how many are queued, the banner says why, **Write now** tries again and **Discard queue** drops them.

- **Give honors stack sizes** (#239): the game's own item tables list how much one slot holds (Spice-infused Fuel Cell 500, most resources 500, Spice Sand 2,500). A Give of more makes several stacks, fills a partial stack of the same item and grade first, and is refused whole when the inventory has no room for them; a stack edited past the stack size is refused.
- **UI pass, round 2** (#236): the editor looks like the rest of the toolkit: a header with a mark and the save's file name as a chip, tabs that read as levels (the active one underlined), rounder cards with a 11 px caps title, value tiles with a border, warnings and notes as banners with a coloured edge, and a consistent button set. - **Journal review fixes** (#230): an edit the journal cannot keep (a script) turned it off for the rest of the session and made Reload now refuse even with nothing pending; the journal is on again once the edits are saved or discarded, and Reload now only refuses when unkept edits are pending. Edits no longer build journal records at all while the journal is off or not enabled.
- **Unsaved edits survive a restart, and Reload now keeps them** (#230): every edit is also kept in a private journal in the editor's own folder (`%APPDATA%\tabr-tau\pending-<id>.json`, mode 0600, deleted when the edits are saved or discarded). It holds what each edit ran (INSERT, UPDATE, DELETE and REPLACE statements with their typed arguments, its description and its row count), nothing else of the save. When the editor starts, or when **Reload now** reads a newer file the game saved, the edits are run again one by one, each in its own transaction through the same write path as a new edit, so the same checks apply; an edit whose statements fail or change a different number of rows than before is not applied, it is listed (what it was and why) so it can be made again. Put-back edits appear in Review & save like any others and saving still needs the review, the game-running checks and an unchanged file. An edit that ran anything the journal does not keep (a script, DDL) turns the journal off for the session instead of keeping part of the edits, and the banner says so. The Discard button still throws the edits away, journal included.
- **The status poll no longer re-reads a changed save every few seconds** (#230): once the editor has found the file on disk to differ, it remembers that file's size and time, so the next polls answer at once instead of reading and hashing the whole save again. A slow status read is what let the automatic refresh decide from a state that an edit had already overtaken.
- **The Give queue survives a refresh** (#230): the items queued under Player > Character > Inventory are kept in the browser's local storage and read back after a reload, so a refresh of the window no longer empties them. What is read back is checked field by field (types, counts, lengths) before it is used. The automatic refresh also asks the server to discard only if nothing is unsaved by the time the request arrives (`ifClean`), so an edit made while the status was being read on a large save is not thrown away with it.
- **The Land Claim Editor removes cells** (#225): click an existing cell to mark it (red), then **Remove marked cells**. Guard rails, enforced by the server as well as shown in the page: a cell that holds a building piece or a placeable can never be removed (the same count Shrink uses; a piece with no owner link counts for every claim, so it keeps the cell), the totem's own cell stays, every cell that stays must remain connected edge to edge to the totem's cell (marking a cell that would cut another off disables the button and says so; mark them together to remove them together), and the request is refused whole when any part fails. It goes through the review pane and the usual backup. Checked by tests on a copy of a claim (empty cells go, a cell with a piece or a placeable blocks the whole request, a cut-off cell is refused); not yet checked in game.
- **The Land Claim Editor shows its compass and axes** (#224): the grid has N, E, S and W at its edges, the totem's two axes drawn as arrows marked +x and +y, a line above it that says which way they run for this base ("Column +x runs South, row +y runs West (the base's yaw is 90°)"), and a cell says its coordinates when you hover it. A base placed at yaw 90 has its grid turned a quarter, so the way to tell which side a cell is on is now on the picture, not an apply-and-look in game. Checked in game: with a base placed facing east (yaw 90), the cell added to the right of the totem in the editor appeared on the right in game, so the editor's direction of the cells is right.
- **Augment items are given with perfect rolls** (#219), as the console does: giving a standalone augment item (`T6_Augment_*`) to the player now writes its roll data with every stat roll at 1 (as many rolls as the augment has) and the best grade, 5, when no grade is chosen (#222; it was grade 1 at first, which showed weak stats in game; a grade you choose is kept). Before, the new item copied the stats of another copy in the save, so it could carry that copy's weaker rolls, or none. Effect indices on the copied roll are kept; gear is unchanged. The data shape is the one the console writes and the editor already writes for pre-applied augments; not yet checked in game.

### Security
- `tasklist` and `rundll32` are started by their full System32 path, `--addr localhost` must resolve to a loopback address, CI runners and Node are pinned and checkouts drop their credentials, the embedded WebView2 loaders are hash-checked by a test, and there is a `SECURITY.md` (#177).
- Foreign-key gate and cascading deletes (F-08 / #9): every edit is checked with `PRAGMA foreign_key_check` before it commits and is refused ("this edit would leave dangling references ...", nothing changed) if it creates a dangling reference the save did not already have (tracked per row, so repairing one orphan while creating another is still refused); references that were already broken in the file are tolerated, and fixing them is allowed. The scan is skipped when an edit changed no rows. Deleting an item that owns an inventory (a bag or chest) now removes that inventory and everything nested in it, exactly as the game's schema declares (`ON DELETE CASCADE`), instead of leaving them behind. Cascading is opt-in per edit (`save.MutateCascade`) and used only for item deletes. `foreign_keys` stays off for ordinary edits (the game's own setting is still to be confirmed by live test T4) and is switched on only for those cascading edits. The SQL console cannot flip it (PRAGMA is refused) and its deletes are gated, not cascaded.
- Single write path (F-05 / #6): `save.Mutate(desc, fn)` is now the only way to change a save. Every edit is one transaction (any error rolls the whole edit back), records its description only if rows changed, and is refused on a read-only save. `Save.Exec`, `ExecScript`, `Tx` and `Log` no longer exist, so the compiler forbids a bare write from `ops`. Every write site in `ops` was migrated; the multi-step ones (`SetItem`, `DeleteItem`, `RepairGear`, `AddSolari`, vendor reset, building repair, Landsraad term) are now atomic and no longer ignore errors. Behaviour changes: editing or deleting a nonexistent item, piece, task or decree, or a raw-table edit that matches no row, is now an error instead of "ok" (idempotent tag/tutorial removals still succeed). `Query`/`Table`/`One` now run on the read-only connection, so a write cannot sneak in through a read helper. `ExecScript` survives only as a test helper. A panic inside an edit now rolls the transaction back instead of wedging the editor.
- Layer 2 review fixes (S0 step 4 and S1): column names read from a save are quoted before use in SQL (a hostile column name could rewrite a search or cell edit); the schema fingerprint now sees triggers/views named `sqlite_*`, recognises virtual tables by `rootpage=0` instead of by SQL text, and compares trigger/view SQL exactly; the read console allows only schema-describing `pragma_*` functions and the write console none; string literals are checked as table names; `applied_patches` and the schema catalogue cannot be edited from the consoles or the cell editor; the UI shows a persistent read-only banner with the reason and shows the commit warning.
- SQL consoles (F-03 / SEC-3, SEC-4, SEC-9, SEC-10, ARCH-7, PR #36): the read console runs on a separate read-only connection with a 1000-row cap and a 5 s timeout; statements are tokenised and vetted (read: one SELECT; write: INSERT/UPDATE/DELETE/REPLACE only, no PRAGMA/ATTACH/DDL/transactions/`load_extension`); a save with unknown or modified triggers, views or virtual tables opens read-only with the reason; table listing never splices save-controlled names into SQL; CSV export neutralises formula cells.
- Durable Commit/Restore (F-07 / #8): backups get unique names, mode 0600, are fsynced and read back to verify; the new save is written to a unique exclusive temp file, fsynced, renamed with retry/backoff, and read back; `force` now skips only the game-running check, never the changed-on-disk check; Restore goes through the same pipeline (no in-place truncation), checks integrity, refuses a backup with patches the current save lacks, and refuses path components in the name; symlinked saves are refused; stale temp files are cleaned at open; a reload problem after a successful write is a warning, not a failed save.
- UI hardening (F-03 / #4, F-04 / #5): the page no longer embeds the API token. A one-time boot link (10 minutes, single use) sets an `HttpOnly; SameSite=Strict` session cookie and redirects; anyone else gets a static locked page. The UI script and CSS moved to separate files so the CSP can be `default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; frame-ancestors 'none'; form-action 'none'` with no `unsafe-inline` and no `unsafe-eval`. All HTML is now built with an escaping `html` tagged template and written only through `setHTML`, which refuses anything else; the 12 inline `style=` attributes became classes; event dispatch tables reject prototype keys.
  Evidence: the old UI was not exploitable against the real schema (every text value went through `esc()`, and the unescaped sites sit on numeric columns of STRICT tables, which reject text) so the audit's original rating of SEC-2 overstated it; it was a latent weakness. With every number in every API response replaced by an attack string (a schema that does not enforce types), the OLD UI injected elements on 5 of 7 tabs and the NEW UI passes all 41 browser-engine tests, including every view under type confusion.
- Web server hardening (F-04, #5): the editor refuses any peer that is not on this computer (a LAN peer sending `Host: localhost` used to get HTTP 200 and the API token; measured by the new test against the old code); `--addr` must be loopback (the `--allow-remote` option this step first had was removed, #58); busy default port falls back to a random loopback port; security headers on every response (`X-Frame-Options: DENY`, `frame-ancestors 'none'`, `nosniff`, `Referrer-Policy: no-referrer`, CORP); `/api/` requires `Content-Type: application/json` on state-changing requests and rejects cross-site `Origin`/`Sec-Fetch-Site`; constant-time token comparison; the server fails closed if the random source fails; read/write/idle timeouts; export filenames are sanitized. Not yet done from F-04: the token is still embedded in the page (bootstrap cookie + CSP script restrictions arrive with the UI step).
- Save decoder is bounded (F-03 / SEC-1, #4): the declared size is checked against a 256 MiB cap before decompression and the stream is read through a limit, so a ~65 KB hostile file no longer allocates ~165 MB. Tests: bomb with a lying header, over-cap header, over-cap file, truncation, size mismatch both ways, wrong flag, non-SQLite payload, round trip at real size, fuzz seeds.
- Layer 1 design audit (tracking issue #24): F-03 and F-04 (S0), F-05, F-07 and F-08 (S1), F-06 (pristine baseline and diff, #7) and the review pane (F-10, #11 slices) are delivered; the `foreign_keys` default stays off for ordinary edits (live test T4 is not run; the editor cascades deletes itself).
