## [Unreleased]

### Added
- Character > Overview no longer repeats what the summary header above it shows (map, account, platform, database ids); it keeps the Solari stack, position and Journey progress (#96).
- Player > Building Sets and Player > Customizations are the console's tabs (#96): the item catalog's building sets (patents and sets) and customization items with a filter, the state of each, and **Give**, which puts the item in the backpack (the game teaches the set or unlocks the cosmetic when it is used). Building sets show **Learned** from the save's learned-sets table (158 of 232 in the real save, 20 of them store-pack sets the catalog does not list, shown but not givable) or **In inventory**; the New buildable pieces list stays below. The save keeps no list of owned customizations that tabr-tau can read, so those only show whether the item is in an inventory, as in the console. Blueprints are tracked in a separate issue until a save has one.
- Player > Research and Player > Crafting are the console's tabs (#96). **Research** lists the character's research tree (372 entries in the real save) in the console's categories with product groups, a filter, and the state of each entry; **Unlock** marks it purchased and adds what it unlocks, a crafting recipe in the known-recipes list or a building set (and its placeable) in the building tables, and a purchased entry whose recipe or set is missing shows **Repair unlock**. Group markers (DA_GRP_) cannot be unlocked as one entry, as in the console. **Crafting** lists the recipes you know (180 in the real save) with their source and limited-use state, plus the ones your research tree can still give (106), with **Unlock** on those. The console finds its recipe list by guessing recipe names from the item catalog's schematics; against the real save that guess matched 15 of the 180 known recipes, while the research tree's RCP_ keys matched all 180, so the research tree is the list used here. Only the one entry is written (the rest of the research and recipe lists is untouched), new recipes have the game's own entry shape, and every change goes through the review pane. Checked on a copy of the real save (unlocking a recipe, its research and two buildings each changed exactly the expected rows); not checked in game yet.
- Player > Skills is the console's Skill Browser (#96): **Skill Point Controls** (earned in total, spent in skills and unspent as stored, and *Set unspent points*, 0 to 100,000 as in the console) and the five schools with every skill's type, a rank bar, the points it holds and a rank control. A rank change writes the points that rank costs (the cumulative ladder in the console's catalog; checked against your skills: rank 2 of a 1-3-6 skill stores 3) and nothing else in the record. Like the console's control it does not touch the unspent points unless you tick *Pay for changes from the unspent points*, which takes the difference from them or gives it back and refuses when they are short. *Restore starter skills* raises a school's first Key skill and first ability to rank 1 and never lowers anything. A skill the catalog does not know (one ships in the game that the catalog omits) is listed with its points but cannot be given a rank. The save does not keep spent plus unspent equal to the total, so the three numbers are shown as stored. Not checked in game yet. The catalog is the console's `admin-skill-modules.json` (MIT, RedBlink), credited in the third-party notices.
- Player > Journey is the console's Journey Browser (#96): **Story, Contract, Codex and Tutorial** lists with readable names (from the console's catalog), the tree shown by indentation with each node's id on hover, status **Complete / Revealed / Incomplete** (Tutorials: Complete / Started / Not Started), a pending-reward marker, the number of gameplay tags each node sets, and a filter over names and ids. Nodes you have no row for yet are listed from the catalog as Incomplete. Complete and Reset work on Story, Codex and Tutorial rows as before (a node takes its children with it); they change the node states only, not the gameplay tags the console also sets, so a completed quest may not give its follow-on effects. Contracts are read-only for now: one is shown complete when every tag it sets is among the character's tags. The old Tutorials card is now the Tutorial list. Names and tags come from the console's `journey-tags.json` (MIT, RedBlink), credited in the third-party notices.
- Player > Admin gets two more of the console's controls (#96). **Faction Assignment** shows the character's faction and changes it to Neutral, Atreides or Harkonnen (the console's three; the save's Smuggler faction is not offered). It writes only the character's one faction row, stamped in microseconds as the game stamps the player's own change; reputation is not touched. **Repair Below %** on Repair Vehicle Durability (1 to 100, default 50 as in the console) raises only the modules of your vehicles that are below that share of their current maximum; modules with no recorded maximum are still skipped. Faction change checked by tests and not yet in game.
- Augments (#96), as in the console: **Character > Inventory** shows an **Augments** button on clothing and weapons that take them, opening an editor with one drop-down per slot (2 on clothing, 3 on a weapon) listing only the augments that fit the item with their best-grade effects, a grade for newly added ones (an augment already on the item keeps its stored grade) and a choice to also unlock the augment slots (the matching specialization keystones, found by name in your save; nothing else about specialization is touched). Choosing none in every slot removes them. **Give item** and the Give Items queue take augments and their grade too, and a plain Give no longer copies another item's augments. The written augment data has the exact shape of the augments in a real save (checked byte for byte against an item from one); it has not been checked in game yet. The compatibility data is the console's `augment-compatibility.json` (MIT, RedBlink; compiled there from method.gg), credited in the third-party notices.
- Give Items queue (#96), on Character > Inventory next to Give item: **Add to queue** collects items (name or template id, quantity, grade), the queue is listed with a remove button on each line, and **Give queued items** adds them all to the backpack in one edit (all or nothing: if one does not fit or is invalid, none are added), up to 50 at a time. The single Give button works as before.
- Player > Vehicles matches the console's Vehicles tab (#96): your vehicles with **Type**, **Lowest condition**, **Fuel** and location, and for the open vehicle (Details) its components with condition and durability and its **Cargo hold** (slots used and the items in it, read-only for now). Condition is each module's current durability against its current maximum, the lowest across modules; a module with no stored maximum shows its value and no percent rather than a guess. The save has no fuel tank size, so fuel is the current amount. Checked read-only on a copy of a real save (Sandbike, lowest condition 95%, empty 15-slot cargo hold).
- Player > Bases matches the console's Bases panel (#94, #96): a table of your bases (ID, Base Name, Base Type, Owner, Map, Generators, Building Pieces, Placeables, Coordinates) and, for the open base, the console's tabs **Power** (generators, windtraps and wind turbines with what they hold, how many are empty and the full amount; Refill generators; the automatic-refill setting), **Water** (each kind of water device with the water stored, capacity and fill; Refill base water), **Inventory** (the base's containers in the console's four groups, Storage, Refining, Crafting and Other, with Open) and **Land Claim Editor** (expand and shrink the claim, as before). Holograms (placement previews) are not counted, as in the console. The permission tabs are not mirrored. The structure tools tabr-tau has and the console's base row does not (structure health, repair all, clear sand, the placeables list and the piece types) moved to the **Extras** tab.
- Character > Inventory matches the console (#96): the character's carried inventories in the console's four groups, **Backpack, Character (worn gear), Loadout (weapons and tools) and Unique schematics**, each with its item count, a filter over name, item id, template and slot, the slots used out of the group's capacity, and a new **Augments** column showing the augments applied to each item by their in-game names (the id and quality are in the tooltip). The view used to list every inventory the character has under its own label (and called type 15 "Weapons / tools" and type 30 "Storage"); it now shows only the console's four, so emotes, contract items and machine slots are no longer listed here (the Database tab still shows them). Editing a stack or grade and deleting an item work as before.
- Give XP and Give currency (#96), on the same Quick rewards card. **Give XP** raises the character's XP and keeps the level data consistent the way the game does: the level follows the XP and a level-n character has n-1 skill points in total (checked against a real save at three levels), so each level gained adds one skill point to both the total and the unspent count; nothing else in the record changes; XP stops at level 200 (344,440). **Give currency** adds to the virtual wallets (Solari Credit, House Credit; a missing wallet is created), which are not the Solari Coin stack in the backpack. Both refuse a save without the record and go through the review pane. Checked on a copy of a real save: +5,000 XP took level 86 to 94 and changed exactly the three level fields; not yet checked in game.
- Give Intel (#96): a **Quick rewards** card on Character > Overview adds Intel for the research tree, never past 2,779 (the console's cap); the result says what was applied when the cap cut it short. It edits the plain `m_TechKnowledgePoints` number in the character's record and leaves the rest of that record alone; a save without the record is refused. Goes through the review pane like every edit.
- Player Summary (#96): the header above the Player tabs, as in the console, read from the save: character, status, map, faction alignment, level and XP (levels from the console's XP table, up to 200), skill points (unspent / total), Intel (of 2,779), health, hydration and spice addiction, platform, Funcom and FLS ids, the database ids, and the currency balances. Solari Credit (the virtual currency) and Solari Coin (the item stacks in your inventory) are shown separately, as in the console. Health shows the current value and "max at least", because the save does not store the maximum. Read-only.

Hagga Basin (and the Deep Desert picture) with your character, your own vehicles, your base, its storage containers and the game's own map markers from the save (3,696 in a real save, grouped as ore and minerals, salvage, plants, enemy camps, places, trainers and House representatives, hazards), discovered ones solid and undiscovered ones faded; drag to pan, scroll to zoom, hover for details, layer toggles, and a table of the marker types on the map. The note under the map says the positions have not been checked against the game for this map: compare a field with the one you see in game and tell me if it is off.

### Changed
- Operator test fixes (#115, #116, #117, #118): the Player summary no longer shows a Guild field (single player has no guilds) and Character > Overview no longer has the Respawn points card; the Live Map layer buttons use the page's own colours so their text can be read (they were dark on dark); on the base list the open base is labelled "Open below" and the other bases get a working Open button (the old button did nothing for the only base); the automatic refill switch for water and power is now on both the Power and the Water tab.
- Every table sorts by any column header (#126): click a header to sort ascending, again for descending, a third time to go back to the original order; an arrow shows the direction. Numbers sort as numbers (9 before 10), editable cells by their value, text naturally, empty cells last. The sort is kept when the table is drawn again after an edit. The Database viewer shows a page at a time, so it sorts the page on screen.
- The Player tab now mirrors the Dune Docker console's Players > Player Name view and its tabs (#96): Character (Overview, Inventory, Reputation), Crafting, Research, Building Sets, Customizations, Skills, Specialization, Journey (with tutorials and player tags), Blueprints, Bases, Vehicles and Admin. Bases and Vehicles are no longer top-level tabs; the top-level tabs are Player, Landsraad, Config, Database and Extras. Each Player tab is meant to hold what the console's tab holds: Admin now has Repair (gear, vehicles), Danger Zone, Movement (Teleport) and Faction Assignment as in the console, with the actions tabr-tau lacks shown disabled and the server-only ones (kick, ban, login queue) left out. Features the console's player view does not have go to the new **Extras** tab (vendor purchase limits for now). The tabs the console has and tabr-tau does not yet (Crafting, Research, Customizations, Skills, Blueprints) say so instead of being left out. Nothing that worked before was removed; features moved: Faction reputation to Character > Reputation, specialization tracks to Specialization, tutorials and tags to Journey, learned building sets to Building Sets, Teleport, Repair gear and Repair vehicles to Admin, vendor limits to Extras. A saved browser tab of Bases or Vehicles opens the matching Player tab.

### Removed
- The read-only Permissions card on the Bases tab (#58) and the `permissions` field of `GET /api/bases`: it was multiplayer scaffolding; in single-player every row has the same access level and the only ranks are the owner.
- Support for non-Windows systems is now stated plainly (#87): the game runs only on Windows and the save lives on the same PC, so the README says Windows 10/11 (64-bit) only, and the macOS/Linux branches that opened the browser are gone. `--web` still opens the browser on Windows (for example when WebView2 is missing).
- The Exchange tab (#58): it only held a second copy of the Solari box (still on Player > Overview) and the vendor purchase limits. The vendor limits and restock cycles moved to **Player > Vendors**; the API paths are now `/api/vendors` and `/api/vendors/reset`.
- The `--allow-remote` flag (#58): the editor has no login and can rewrite your save, and nothing needs it to be reachable from another machine, so it now only ever listens on this computer and only accepts connections from it. A non-loopback `--addr` is refused outright.

### Fixed
- CI now also runs `go vet` and `go test` on a Windows runner (#85); before, Windows-only code was only cross-compiled, which let a Windows-only test failure (#82) through.
- A build made on Windows no longer opens every real save read-only (#104). The editor compares the game's triggers and views with the built-in schema to refuse saves with hidden logic; the built-in schema file is CRLF on a Windows checkout while the game's own saves use LF, so the same trigger looked "modified" and all edits were refused ("This save is read-only. modified trigger actor_fgl_entities_cleanup_orphaned_entities"). Line endings are now ignored in the comparison and the schema file is pinned to LF. Linux and release builds were not affected.
- The Vehicles tab lists only your own vehicles (#92). A vehicle's owner is the owner-rank row of its permission record for your character (`actors.owner_account_id` is empty for every vehicle in real saves); the many grade-0 vehicles the game places in the world have no such record and are no longer listed, repaired by **Repair all vehicles** or movable with **Bring to me**. The tab says how many world vehicles are hidden. Recovered and backup vehicles are shown for your character only. A vehicle with no owner record counts as a world vehicle.
- Bases > Storage lists only the storage containers that belong to your base (#75, #74). It used to list every inventory of every non-player actor (120 rows in a real save, 13 of them storage): generator and turbine fuel slots, refineries and fabricators, vehicles, CHOAM terminals and the world's loot containers. Now a container is listed when it is a storage building type (Storage Container, Medium Storage Container, Chest, Small Storage Container) whose owner entity is your base's totem, as the console does. It shows your own name for the container when you set one, its type, and items out of its slot capacity, instead of the sum of stack sizes that read oddly ("Total units"). Refineries and fabricators are no longer in this list.
- Saving is blocked only while a single-player session is active, not whenever the game is open (#65). The game process stays up in multiplayer and at the menu, and only a single-player session holds the save. The editor reads the game's log (`Saved/Logs/DuneSandbox.log`): a local `...Survival_1?listen` map starts a session; a `?closed` or remote `ip:port` browse, `RequestExit` or `Log file closed` ends it; the game's final write lands about 3 s later, so Save also waits 15 s. Checked against 11 real logs: every start pairs with an end. Failing closed is unchanged: if the game runs and the log cannot be read, Save is blocked and the banner says why. Config edits still refuse while any Dune process runs, because the game rewrites its configs on exit.
- The running-game check matched one guessed process name that was never verified, so on a real machine it could say "not running" while the game was open and Save then failed late with "changed on disk" (#52). It now matches any process whose name starts with `Dune`, and the banner and refusals name what was found. If the check itself cannot run, Save is blocked and the banner says why, instead of assuming the game is closed. Verified on a real machine: the game runs as `DuneSandbox.exe`, `DuneSandbox_BE.exe` and `DuneSandbox-Win64-Shipping.exe`; the launcher (`GT.Launcher`) does not match, and leaving single-player does not end the game process.

### Added
- Optional refill when the editor opens (#63 step 2): the Bases tab has an **Automatic refill** switch (off by default, remembered in `%APPDATA%\tabr-tau\settings.json`; turning it on asks first). When on, opening the editor refills base water and generators and **saves straight away**, without the Review & save step, so the refill applies the next time the game loads. This is a deliberate exception to "Save only from the review pane", for this opt-in setting only (operator decision, 2026-10-08). The write still goes through the whole pipeline (single-player check, changed-on-disk check, integrity check, backup first, read-back); it is skipped while a single-player session is running or when there are unsaved edits, and if the write is refused the edits stay pending under Review & save with the reason shown. The refills no longer leave an empty pending edit behind when there is nothing to fill.
- Shrink a land claim (#57 follow-up; verified in game 2026-10-08): the Bases tab claim card has **Shrink claim**, which removes every stored cell outside a chosen square (down to the totem's own cell). A cell that holds building pieces or placeables is never removed; the request is refused and says how many pieces block it. The piece-to-cell match uses the claim's own frame (offset from the claim origin, turned by minus the claim yaw, divided by the 5,120-unit cell, rounded; no axis flips), and the card shows how many pieces are inside and outside the claim. Verified: removing the 8 extra cells of an expanded claim worked, and the game then added its own cells when 4 Staking Units were placed (and raised the vertical level to 5 with 5 Vertical Staking Units), using the same two tables, with all pieces still in the totem's own cell.
- Land claim size (#57; verified in game 2026-10-08): the Bases tab has an **Expand claim** control per totem. It adds every missing cell up to a 3x3 .. 11x11 square around the totem (one cell is 10x10 foundations) in `landclaim_segments`, and can raise `totems.landclaim_vertical_level` (0 to 5). Expansion only: cells are never removed and the level never lowered; the square is always connected edge to edge. Same tables and rules as the Dune Docker console's Land Claim Editor. Verified: a one-ring (3x3) expansion of an Advanced Sub-Fief loaded, allowed building outside the old claim, and was still stored after the game rewrote its save.
- Item names everywhere (QA, F-20 / #21): one embedded catalog (`internal/catalog`, 2,551 items: template id, in-game name, category) feeds a single item picker used by Give item on the Player tab and by the storage Add item box (which had an empty list), and the item tables (inventory, storage, vendors, Landsraad rewards) show the in-game name with the template id on hover. A name shared by several items is told apart by its id. An id in your save that the catalog does not know stays selectable by its id, and a typed template id is still accepted. The names come from the Dune Awakening Docker item catalog (MIT, RedBlink; its licence is reproduced in the notices); only id, name and category are kept.
- Base upkeep and vehicle repair (#63, #56; verified in game 2026-10-08): Bases tab buttons **Refill base water** (cisterns, windtraps and blood purifiers to capacity, via `FWaterStorageComponent.m_WaterStored`; capacities from the Dune Docker console's table) and **Refill generators** (fuel and spice generators topped up to a full stack of 500, an empty generator gets a stack); Vehicles tab **Repair all vehicles** (every module's `CurrentDurability` raised to its `DecayedMaxDurability`). Wear that lowered the decayed maximum itself is not undone because the save does not store each module's original maximum; modules with no recorded maximum are counted and left alone. Wind turbines are not handled yet. Base "Repair all" is unchanged. The game loaded the edited save, showed the values, and kept them after rewriting its own save (water and fuel at the written levels, one Fuel Cell burned by a running generator, all 74 repairable vehicle modules at their maximum).
- Refill containers (#55): a Player-tab button fills every water container the player carries to its capacity. The fill level is the item's own `FFillableItemStats.CurrentAmount` (an empty container has no such key). Verified live on 2026-10-08: the game loaded the edited values and kept them after rewriting the save. Capacities (Literjon 1000, Mk6 20000, Decaliterjon 10000, Hajra Mk1-Mk6 1500-3000) are read from the game; a water container with a fill record that is not in the table is skipped and listed, never guessed (an empty unlisted one has no record to recognise it by and is left alone). Blood sacks are left alone (#60).
- Tiered confirmations (S2 slice 2, F-10 / #11): the bare browser `confirm()` dialogs are replaced by an in-app question that states the consequence. Reversible edits ask nothing (they are pending, listed in the review, and Discard undoes them). Deleting an item, discarding, reloading, deleting a config line, restoring a config backup, resetting vendor limits and completing a Landsraad task ask first. Far-reaching actions (repair every base piece, clear sand, a raw SQL write, restoring a backup over the save) also need a word typed. Escape or a click outside cancels. Success messages now say "(not saved yet)" while edits are pending, so a green toast is not mistaken for "in the game".
- Native Windows window: on Windows the editor opens in its own window (Microsoft Edge WebView2, via `github.com/jchv/go-webview2`, pure Go, no C compiler) instead of a browser tab. A native Open dialog picks the save when none is found, startup errors appear in message boxes, WebView2's profile lives under `%LOCALAPPDATA%\tabr-tau\webview2` (never next to the exe), developer tools and the context menu are off, and a missing WebView2 runtime shows a message box with instructions (no silent background server). `--web` forces the browser; `--allow-remote` needs it. Closing with unsaved edits asks first: the window host destroys the window directly, so the native window intercepts the close itself (a Yes/No box, default No) and the page asks via beforeunload in browser mode. The build is a GUI-subsystem exe that reattaches to the parent console (only for streams that were not redirected) so `diff` and the other subcommands still print; a crash in window mode is reported in a message box; an injected guard refuses `window.open` and links that leave the editor's origin. The Microsoft WebView2 loader notice is included. CI cross-compiles and vets the Windows build and runs govulncheck against it; Third-party licence texts for every module in the binary are embedded in the exe (`tabr-tau licenses`, source `internal/notices/THIRD-PARTY-NOTICES.md`, with a test that fails when a dependency has no notice). **Not yet verified on a real Windows machine** - the window code cannot run on the Linux build host; it is compile-checked only.
- Review pane (S2 slice 1, F-10 / #11): the header button is now "Review & save". It opens a pane listing every edit and the row/value changes inside game.db; "Save to game" exists only there. The server enforces it: `/api/save/commit` needs the `reviewed` token returned by `/api/save/review` (a hash of the pending edits), and refuses a save with no token or with edits that changed after the review. A persistent banner (polled every 5 s) says when the game is running and disables Save with the reason. Errors stay on screen until dismissed. The UI still never sends `force`; the HTTP API no longer accepts it. A "changed on disk" failure keeps the edits listed and offers "Reload from disk".
- Pristine baseline and review data (F-06 / #7): the editor keeps an immutable decoded copy of the save as loaded, records every edit as a structured op (description, rows changed, time), and can compare baseline against working copy. New package `internal/diff` (Go port of `tools/snapdiff.py`, which stays for the live-test scripts): row-level add/remove/modify per table (rows matched and compared on raw values, typed keys), JSON-path diffs inside JSONB columns (integers compared exactly, fractions with a tolerance), hex diffs for opaque blobs, multiset handling for tables without a primary key, noise-column filter, row caps with true totals (clamped to 1000). Identifiers are masked in the output only, by default: personal columns (platform/Funcom ids, names, guild identifier, anything named like `*steam*`, `*identifier*`, `*email*`), any 15+ digit number whatever its type (text, integer, float, JSON number, JSON key), and long digit runs in edit descriptions; masking never hides a change (an edited `funcom_id` is listed as `<redacted>` -> `<redacted>`), and a test fails if a new column that looks personal is not classified. `GET /api/save/review` returns the edits and the diff; `tabr-tau diff <before> <after>` does the same for two files, read-only, with the Python tool's flags. A failed reload no longer leaks temp files or half-closes the save, and a failed reload after Commit or Restore disables further edits. The review screen that uses all this is the S2 slice above.

### Security
- Foreign-key gate and cascading deletes (F-08 / #9): every edit is checked with `PRAGMA foreign_key_check` before it commits and is refused ("this edit would leave dangling references ...", nothing changed) if it creates a dangling reference the save did not already have (tracked per row, so repairing one orphan while creating another is still refused); references that were already broken in the file are tolerated, and fixing them is allowed. The scan is skipped when an edit changed no rows. Deleting an item that owns an inventory (a bag or chest) now removes that inventory and everything nested in it, exactly as the game's schema declares (`ON DELETE CASCADE`), instead of leaving them behind. Cascading is opt-in per edit (`save.MutateCascade`) and used only for item deletes. `foreign_keys` stays off for ordinary edits (the game's own setting is still to be confirmed by live test T4) and is switched on only for those cascading edits. The SQL console cannot flip it (PRAGMA is refused) and its deletes are gated, not cascaded.
- Single write path (F-05 / #6): `save.Mutate(desc, fn)` is now the only way to change a save. Every edit is one transaction (any error rolls the whole edit back), records its description only if rows changed, and is refused on a read-only save. `Save.Exec`, `ExecScript`, `Tx` and `Log` no longer exist, so the compiler forbids a bare write from `ops`. Every write site in `ops` was migrated; the multi-step ones (`SetItem`, `DeleteItem`, `RepairGear`, `AddSolari`, vendor reset, building repair, Landsraad term) are now atomic and no longer ignore errors. Behaviour changes: editing or deleting a nonexistent item, piece, task or decree, or a raw-table edit that matches no row, is now an error instead of "ok" (idempotent tag/tutorial removals still succeed). `Query`/`Table`/`One` now run on the read-only connection, so a write cannot sneak in through a read helper. `ExecScript` survives only as a test helper. A panic inside an edit now rolls the transaction back instead of wedging the editor.
- Layer 2 review fixes (S0 step 4 and S1): column names read from a save are quoted before use in SQL (a hostile column name could rewrite a search or cell edit); the schema fingerprint now sees triggers/views named `sqlite_*`, recognises virtual tables by `rootpage=0` instead of by SQL text, and compares trigger/view SQL exactly; the read console allows only schema-describing `pragma_*` functions and the write console none; string literals are checked as table names; `applied_patches` and the schema catalogue cannot be edited from the consoles or the cell editor; the UI shows a persistent read-only banner with the reason and shows the commit warning.
- SQL consoles (F-03 / SEC-3, SEC-4, SEC-9, SEC-10, ARCH-7, PR #36): the read console runs on a separate read-only connection with a 1000-row cap and a 5 s timeout; statements are tokenised and vetted (read: one SELECT; write: INSERT/UPDATE/DELETE/REPLACE only, no PRAGMA/ATTACH/DDL/transactions/`load_extension`); a save with unknown or modified triggers, views or virtual tables opens read-only with the reason; table listing never splices save-controlled names into SQL; CSV export neutralises formula cells.
- Durable Commit/Restore (F-07 / #8): backups get unique names, mode 0600, are fsynced and read back to verify; the new save is written to a unique exclusive temp file, fsynced, renamed with retry/backoff, and read back; `force` now skips only the game-running check, never the changed-on-disk check; Restore goes through the same pipeline (no in-place truncation), checks integrity, refuses a backup with patches the current save lacks, and refuses path components in the name; symlinked saves are refused; stale temp files are cleaned at open; a reload problem after a successful write is a warning, not a failed save.
- UI hardening (F-03 / #4, F-04 / #5): the page no longer embeds the API token. A one-time boot link (10 minutes, single use) sets an `HttpOnly; SameSite=Strict` session cookie and redirects; anyone else gets a static locked page. The UI script and CSS moved to separate files so the CSP can be `default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; frame-ancestors 'none'; form-action 'none'` with no `unsafe-inline` and no `unsafe-eval`. All HTML is now built with an escaping `html` tagged template and written only through `setHTML`, which refuses anything else; the 12 inline `style=` attributes became classes; event dispatch tables reject prototype keys.
  Evidence: the old UI was not exploitable against the real schema (every text value went through `esc()`, and the unescaped sites sit on numeric columns of STRICT tables, which reject text) so the audit's original rating of SEC-2 overstated it; it was a latent weakness. With every number in every API response replaced by an attack string (a schema that does not enforce types), the OLD UI injected elements on 5 of 7 tabs and the NEW UI passes all 41 browser-engine tests, including every view under type confusion.
- Web server hardening (F-04, #5): the editor refuses any peer that is not on this computer (a LAN peer sending `Host: localhost` used to get HTTP 200 and the API token; measured by the new test against the old code); `--addr` must be loopback, and a non-loopback bind needs `--allow-remote` plus typing `I UNDERSTAND`; busy default port falls back to a random loopback port; security headers on every response (`X-Frame-Options: DENY`, `frame-ancestors 'none'`, `nosniff`, `Referrer-Policy: no-referrer`, CORP); `/api/` requires `Content-Type: application/json` on state-changing requests and rejects cross-site `Origin`/`Sec-Fetch-Site`; constant-time token comparison; the server fails closed if the random source fails; read/write/idle timeouts; export filenames are sanitized. Not yet done from F-04: the token is still embedded in the page (bootstrap cookie + CSP script restrictions arrive with the UI step).
- Save decoder is bounded (F-03 / SEC-1, #4): the declared size is checked against a 256 MiB cap before decompression and the stream is read through a limit, so a ~65 KB hostile file no longer allocates ~165 MB. Tests: bomb with a lying header, over-cap header, over-cap file, truncation, size mismatch both ways, wrong flag, non-SQLite payload, round trip at real size, fuzz seeds.
- Go toolchain raised to 1.26.6 (six reachable standard-library vulnerabilities found by govulncheck: GO-2026-5037, 5039, 5856, 5972, 6089, 6090).
- Findings from the Layer 1 audit are tracked in issue #24. Fixed so far: F-03 and F-04 (S0), F-05, F-07 and F-08 (S1 slices 1-3).
  **Still open:** F-06 (pristine baseline and diff, #7), the `foreign_keys=ON` decision (needs live test T4), and the S2 safety UX (F-10). Until those land, take a
  backup before large edits (the editor does this on every save), and do not open saves from untrusted sources.
