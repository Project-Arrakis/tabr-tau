It names the pull request or test that shows each one; #301, #302, #304 and #324 closed the gaps found on the way.
- The 2026-09-30 design audit register is reconciled with the code (#24, F-01 to F-22): each finding was checked again against the current code, tests, CI and repository settings; 13 of 22 are fixed, 2 are accepted risks (the removed review pane, `foreign_keys` left off), 7 are open and low or waiting for the live game or the owner. Three statements of the design plan that were no longer true (authorizer and `trusted_schema`, the refusal of online-server folders, IPv6) are corrected.
- **Three guards written as tests** (#23, #180, register 2026-09-30 F-22 and register 2026-10-15 QA-3): the claim that the editor's own code makes no outbound connection now fails the build if shipped code uses an HTTP client or dials out (the one name lookup, of `localhost`, is listed by name); writing a config entry back with the value it has leaves the file byte for byte as it was (CRLF or LF, byte-order mark, comments); and `TutorialSet` and `TagSet` are tested to touch only the character's own rows (a mutant that dropped the player from either delete is caught). No behaviour changed.

- **The journal of queued edits keeps what the edits ran** (#251, audit finding DBA-10): a nil blob stays NULL (an empty blob stays a blob), text that is not valid UTF-8 comes back byte for byte (it used to be rewritten with U+FFFD), a single-precision float comes back as the value that was stored (it used to come back as the shorter decimal, 0.1 instead of 0.10000000149011612), and a ';' inside a quoted value, a quoted name or a comment no longer counts as a second statement, which turned the journal off and left the queue unable to be put back onto a newer file. A journal that cannot be written (its folder cannot be made, the disk is full, the rename fails) is turned off with the reason, which the page shows, and it is flushed to the disk before it replaces the old one. Before, a failed write was ignored and the page went on saying the queue was kept.
- **An edit's answer says whether it was written or queued, and a refusal has a code** (#262, audit finding ARCH-15): every edit request that leaves edits to write now answers with `"outcome": "written"` (the edit is in the game's file) or `"outcome": "queued"` (accepted, written when the file can be), next to the fields it always had. A refusal keeps its `error` text and now also carries a stable `code` with a status that fits: `changed_on_disk` 409, `queue_held` 409, `queued` 409, `game_running` 409, `read_only` 409 (these two were 400 when this was written; #334 made them 409), `bad_argument` 422, `not_found` 404, `bad_request` 400 (an error with none of these is still a 400 without a code). The page reads the outcome of the answer to decide whether a message says "queued" (it used to read a status that could be seconds old) and keeps the code and status of a refusal; it never reads the words of a message.
- The 2026-10-22 audit register marks the findings fixed by #274, #280, #287, #292 to #299 (E1, E4, E7, E8, E9, E11 and E12; #251, #254, #257 to #259, #261, #262): DBA-16 (table definitions and applied patches at open) and NET-8 (navigation hook of the native window) stay open with the reason written in their rows, DBA-8 is partly fixed. No code changed.
- **Provenance and notice for the data taken from the game's own tables** (#260, audit finding GRC-6): `internal/notices/THIRD-PARTY-NOTICES.md` and `internal/catalog/PROVENANCE.md` say which two embedded files (`stacks.json`, `customization_unlocks.json`) come from the game's item tables, what they hold, how big they are, and what is not recorded about them (the game build, the date, the tool, the licence position). Tests fail when the notice is missing or the sizes in PROVENANCE.md no longer match the data.
- The 2026-10-22 audit register marks the findings fixed by #270, #271, #272, #277 and by the repository settings changed on 2026-10-22 (required checks `windows` and `ui`, private vulnerability reporting), each with the evidence (#256, audit findings CLD-4, CLD-5, CLD-6, CLD-8, CLD-13, QA-18, QA-1, DBA-2, DBA-3, DBA-5; GRC-18 partly). `SECURITY.md` needed no change: the channel it names is now on.
- **The game-running check is made again right before the file is replaced, and the on-disk check is taken before the read** (#257, audit findings DBA-15, DBA-17 and ARCH-8): the check that no single-player session is active was made once, before the edits were encoded, backed up and written to a temp file, which on a large save is seconds in which a session can start and the game rewrite the file. It is now also made right before the rename; if a session began in between, nothing is written and the edits stay queued (the temp file is removed). The size and time of the save file are now taken before its content is read, so a game save that lands between the two is seen as a change (taken after, the new time was recorded against the old content and "changed on disk" could say no for a file newer than the loaded one). The automatic write no longer starts a second process check while it holds the save's lock (Flush has just made one, and the new check right before the rename is the one that counts); the rest of the lock (hash, encode, backup, rename retries) is kept on purpose and the reason is written at the top of `commit`.
- **Tests of the write path** (#262, audit findings QA-2, QA-4, QA-15): the answer of an attempt to write now has a test for each way it can end without a write (the edits cannot be put back, the queue is held with the conflict named, the game saved while the file was being written, the write failed, the save is read-only) and for the warning of a file that was written but could not be read back; a cascading delete (a bag and what it holds) is tested through the journal, at start and after the game saved; the journal's two size limits are tested; the flush route and the write after every edit request have tests of their own. No change in behaviour.
- **Decoded copies of the save are kept in a folder of their own and swept** (#259, audit findings SEC-3, SEC-12 and NET-5): the plain copy of the save the editor works on (it holds the account and platform ids) is made in `tabr-tau-work` in the temp folder, created for the owner alone, and named by the process that made it. It is removed when the editor closes, including on Ctrl+C in a terminal; a copy that a crash or a kill left behind is removed at the next start once its process is gone, and copies older versions left loose in the temp folder are removed when a day old (the operator's temp folder held 27). SECURITY.md now states, under the known limits, that the queue of waiting edits is a plain file in the roaming profile and is replayed without the console's checks, that the decoded copy exists, and what the cookie's reach is (and how to avoid it with `--web`).
- **The Live Map tab is the Saved map** (#268, audit finding UX-34): the tab and its card are called Saved map and say they show the save as of its last write. Marker names are words ("House Representative Argosaz", "Azurite Pickup"), the game's own id is in the tooltip, and the hover labels the coordinates ("x -100000, y 52000"). The picture follows the size of the canvas and the screen's pixel ratio (sharp on a dense screen, not stretched when the window changes). The view (centre and zoom) is kept when the page is drawn again, including by the automatic refresh, and Hide undiscovered markers only redraws instead of fetching the map again. There are Zoom in, Zoom out and Fit buttons; on the focused map + and - zoom, 0 fits and the arrow keys move; the canvas has an accessible name.
- **Review-era leftovers removed** (#261, audit findings ARCH-6 and QA-17; the pristine copy of the save was already gone in #287): the internal write function no longer has a `force` argument that nothing ever set (the game-running check cannot be skipped by any caller), the exported `Save.Commit` that only tests called is now `CommitForTests` in the test-hook file (a guard test fails if shipped code calls it), and the comments that still described a review pane or a review-before-save screen (the journal, the diff package, the batch give, the auto-refill setting) say what the editor does now.
- **Bulk base actions ask first, inline edits say what changed** (#254, audit findings GRC-2 and UX-29): Refill power, Refill base water, Repair every base and Clear sand on every base change every base on one click, since the review step went. The first press now turns the same button into "Yes, ..." for eight seconds (a press elsewhere, Escape or leaving the button cancels; a screen reader is told), the second press runs it. There is no dialog, so the keyboard is never trapped. A value edited in its box (stack, grade, reputation, a skill rank, a config value, a database cell) reports "old -> new" and how to put the old one back (type it again; the backup holds the file as it was). There is no undo of its own.
- **Editor accessibility** (#250, audit findings UX-32 and UX-41): a question is a named dialog (labelled by its title, described by its text); while it is open the page behind it is inert and does not scroll, and focus returns to the button that asked. Enter in a filter box (Inventory, Journey, Research, Crafting, Customizations, Database, the teleport finder) runs the filter and leaves the cursor in the box. Table headers that sort can be reached with Tab, used with Enter or Space, and announce their order. Buttons, inputs and selects are at least 32 px tall. The light theme's muted text and green are darker (the muted text on the beige tiles was 4.08:1; now at least 4.75:1, and a test keeps every light text colour above 4.5:1). The browser tab has an icon and names the open page.
- **Bounded work on the save's lock** (#257, audit findings SEC-11, QA-13 and NET-13): a statement typed into the write console is stopped after 15 seconds (it ran for as long as it liked, with the save locked) and nothing is changed; a give of an item that holds one per slot no longer reads the whole inventory again for every piece (500 pieces took 0.23 s, 2,000 took 5 s; the inventory is now read once per give), and one give makes at most 1,000 separate stacks (a bigger one is refused whole with a sentence that says what to do; no inventory the game builds has room for more); an edit request may take up to ten minutes to be answered, not the two minutes of the server's write timeout, so a very large save that is written late is not reported to the page as a network error.
- **Small screens and a loading line** (#266, audit finding UX-37): under 720 px wide the header and the warning banner scroll away instead of staying fixed (they took about 200 px of an 800 px screen), the header is tighter, cards and tables use less padding, controls and toasts fit the width, and the sub-tab rows scroll sideways instead of growing. Until the first view is drawn the page says "Loading the save...", and says so when the editor does not answer (with Try again). The empty file-name chip is hidden until the name is known.
- **A record of every write** (#254, audit findings GRC-3 and SEC-14): after each write the editor appends one line to `write-log.jsonl` in its own folder (`%APPDATA%\tabr-tau`): the time, how many edits, what they were in words, and the name of the backup taken before. The log holds no values from the save (a statement typed into the SQL console is not copied, a number of 15 digits or more is replaced, each description is cut at 200 characters), is created with owner-only permissions, and at 256 KB becomes `write-log.1.jsonl` with a new file started, so there are never more than two. If a line cannot be written the write stands and the banner says the record is missing. `SECURITY.md` now states the accepted risk of a write on every accepted request and the controls that stand in its place, and lists the log among the guards.
- **Specialization on a new save, and empty tables** (#264, audit findings UX-36 and UX-38): while no track has a number in the save, the Specialization page says so, says what to do (earn a little XP in a track in the game, then come back and assign it) and that keystones work now, and each disabled button says why. "Advanced: set a raw row" is folded and asks before it writes. Tables that can be empty say what is empty (no placeables, no building pieces, no decrees, no backups of this file, no skills in this school) instead of "Nothing to show here.".
- Documents and page text describe the write-as-you-go model only (#255, audit findings GRC-1, GRC-12, GRC-13, GRC-14, UX-28, UX-40, QA-16): SECURITY.md lists the guards that stand in place of the removed review pane; the SQL, delete and backup texts say that an edit is written to the game's file as it is made (after a backup) or queued while the file cannot be written; the older changelog entries below that describe the review pane carry a note that #238 replaced it; the audit register records what replaced the control, and `docs/control-removal.md` says how a change that removes a register control is handled.
- **Edits are written as they are made** (#238): there is no Review & save step. After every edit the editor writes the game's file (a backup first, taken once for a burst of edits and kept for the newest 60; the same checks as before: no single-player session, the file unchanged, an integrity check, a read-back). While the file cannot be written (the game is in a single-player session, the save's location is not confirmed) the edits are queued in the journal and written by themselves, a few seconds after the file can be, onto the game's newer file when it saved meanwhile. The header shows how many are queued, the banner says why, **Write now** tries again and **Discard queue** drops them.
- CI is steadier against runner flakes (#269): the PSScriptAnalyzer install is tried three times, and the Windows tests have 20 minutes (the job 30) after a runner with a slow disk took over twelve and failed a main run.
- The folder of agent worktrees (`.claude/`) is ignored, so a `git add -A` cannot commit copies of the repository (#263, audit finding E13).
- **A cell edited in the tables view is checked against what the table showed** (#259, audit finding SEC-7): the Database tables view addressed a row by its row number or key and sent only the new value, so a view that was out of date (the game saved, or queued edits were put back onto a newer file) could overwrite a different cell without a word. The page now sends the text the cell showed with the edit; if the cell holds something else, nothing is changed, the answer is a 409 with the code `conflict`, the page puts the old text back and loads the table again. The comparison reads the text the way the column does (a number column reads "5" as 5, so 5.0 matches; an empty cell is NULL or empty text). A caller that sends no expected text is served as before.
- **Give honors stack sizes** (#239): the game's own item tables list how much one slot holds (Spice-infused Fuel Cell 500, most resources 500, Spice Sand 2,500). A Give of more makes several stacks, fills a partial stack of the same item and grade first, and is refused whole when the inventory has no room for them; a stack edited past the stack size is refused.

- **Journal review fixes** (#230): an edit the journal cannot keep (a script) turned it off for the rest of the session and made Reload now refuse even with nothing pending; the journal is on again once the edits are saved or discarded, and Reload now only refuses when unkept edits are pending. Edits no longer build journal records at all while the journal is off or not enabled.
- **Unsaved edits survive a restart, and Reload now keeps them** (#230): every edit is also kept in a private journal in the editor's own folder (`%APPDATA%\tabr-tau\pending-<id>.json`, mode 0600, deleted when the edits are saved or discarded). It holds what each edit ran (INSERT, UPDATE, DELETE and REPLACE statements with their typed arguments, its description and its row count), nothing else of the save. When the editor starts, or when **Reload now** reads a newer file the game saved, the edits are run again one by one, each in its own transaction through the same write path as a new edit, so the same checks apply; an edit whose statements fail or change a different number of rows than before is not applied, it is listed (what it was and why) so it can be made again. Put-back edits appear in Review & save like any others and saving still needs the review, the game-running checks and an unchanged file. An edit that ran anything the journal does not keep (a script, DDL) turns the journal off for the session instead of keeping part of the edits, and the banner says so. The Discard button still throws the edits away, journal included. (Superseded by #238: there is no Review & save step. The journal now holds only the edits that are waiting for the file to become writable; edits that can be written are written as they are made, and the journal is removed once they are.)
- **The status poll no longer re-reads a changed save every few seconds** (#230): once the editor has found the file on disk to differ, it remembers that file's size and time, so the next polls answer at once instead of reading and hashing the whole save again. A slow status read is what let the automatic refresh decide from a state that an edit had already overtaken.
- **The Give queue survives a refresh** (#230): the items queued under Player > Character > Inventory are kept in the browser's local storage and read back after a reload, so a refresh of the window no longer empties them. What is read back is checked field by field (types, counts, lengths) before it is used. The automatic refresh also asks the server to discard only if nothing is unsaved by the time the request arrives (`ifClean`), so an edit made while the status was being read on a large save is not thrown away with it.

Web tests cover the redraw after an action, the controls, the move to another tab and the refresh.

### Security
- **The save's own triggers and views are not trusted** (#4, register 2026-09-30 F-03): the connections that open the save now run with SQLite's `trusted_schema` switched OFF (it defaults to ON), so a trigger, view or generated column in a save can only call functions SQLite considers innocuous. The game's own trigger is unaffected. The schema check that makes a save with unknown objects read-only stays as the first defence. Test: `TestTheSavesSchemaIsNotTrusted`.
- **Neither SQL console accepts `zeroblob` or `randomblob`** (#40, register 2026-10-07 S8): one call allocated up to a gigabyte (a probe took 760 MB for `zeroblob(400000000)`), and the read console read the whole value before it cut it down for display. Both functions are refused like `load_extension`. Test: `TestConsolesRefuseFunctionsThatAllocateHugeValues`.
- `tasklist` and `rundll32` are started by their full System32 path, `--addr localhost` must resolve to a loopback address, CI runners and Node are pinned and checkouts drop their credentials, the embedded WebView2 loaders are hash-checked by a test, and there is a `SECURITY.md` (#177).
- Foreign-key gate and cascading deletes (F-08 / #9): every edit is checked with `PRAGMA foreign_key_check` before it commits and is refused ("this edit would leave dangling references ...", nothing changed) if it creates a dangling reference the save did not already have (tracked per row, so repairing one orphan while creating another is still refused); references that were already broken in the file are tolerated, and fixing them is allowed. The scan is skipped when an edit changed no rows. Deleting an item that owns an inventory (a bag or chest) now removes that inventory and everything nested in it, exactly as the game's schema declares (`ON DELETE CASCADE`), instead of leaving them behind. Cascading is opt-in per edit (`save.MutateCascade`) and used only for item deletes. `foreign_keys` stays off for ordinary edits (the game's own setting is still to be confirmed by live test T4) and is switched on only for those cascading edits. The SQL console cannot flip it (PRAGMA is refused) and its deletes are gated, not cascaded.
- Single write path (F-05 / #6): `save.Mutate(desc, fn)` is now the only way to change a save. Every edit is one transaction (any error rolls the whole edit back), records its description only if rows changed, and is refused on a read-only save. `Save.Exec`, `ExecScript`, `Tx` and `Log` no longer exist, so the compiler forbids a bare write from `ops`. Every write site in `ops` was migrated; the multi-step ones (`SetItem`, `DeleteItem`, `RepairGear`, `AddSolari`, vendor reset, building repair, Landsraad term) are now atomic and no longer ignore errors. Behaviour changes: editing or deleting a nonexistent item, piece, task or decree, or a raw-table edit that matches no row, is now an error instead of "ok" (idempotent tag/tutorial removals still succeed). `Query`/`Table`/`One` now run on the read-only connection, so a write cannot sneak in through a read helper. `ExecScript` survives only as a test helper. A panic inside an edit now rolls the transaction back instead of wedging the editor.
- Layer 2 review fixes (S0 step 4 and S1): column names read from a save are quoted before use in SQL (a hostile column name could rewrite a search or cell edit); the schema fingerprint now sees triggers/views named `sqlite_*`, recognises virtual tables by `rootpage=0` instead of by SQL text, and compares trigger/view SQL exactly; the read console allows only schema-describing `pragma_*` functions and the write console none; string literals are checked as table names; `applied_patches` and the schema catalogue cannot be edited from the consoles or the cell editor; the UI shows a persistent read-only banner with the reason and shows the commit warning.
- **The write log says what it holds** (#306, review finding B3): SECURITY.md and README said the write log "holds no values from the save" and that it has owner-only permissions. The descriptions carry game ids and amounts ("Give 500 x ... to container 12"), and the permission mode does nothing on Windows. Both texts now say what is true. The log also leaves out the primary-key value of an edited row in the Database view, long hexadecimal ids and GUIDs, and file paths (a warning's text can carry one), and a restore of a backup is now recorded in it like any other write.
- SQL consoles (F-03 / SEC-3, SEC-4, SEC-9, SEC-10, ARCH-7, PR #36): the read console runs on a separate read-only connection with a 1000-row cap and a 5 s timeout; statements are tokenised and vetted (read: one SELECT; write: INSERT/UPDATE/DELETE/REPLACE only, no PRAGMA/ATTACH/DDL/transactions/`load_extension`); a save with unknown or modified triggers, views or virtual tables opens read-only with the reason; table listing never splices save-controlled names into SQL; CSV export neutralises formula cells.
- Durable Commit/Restore (F-07 / #8): backups get unique names, mode 0600, are fsynced and read back to verify; the new save is written to a unique exclusive temp file, fsynced, renamed with retry/backoff, and read back; `force` now skips only the game-running check, never the changed-on-disk check; Restore goes through the same pipeline (no in-place truncation), checks integrity, refuses a backup with patches the current save lacks, and refuses path components in the name; symlinked saves are refused; stale temp files are cleaned at open; a reload problem after a successful write is a warning, not a failed save.
- **A register row no longer prints a mailbox address** (#306, review finding B4): the 2026-10-22 audit register (row CLD-12, the author address on 30 public commits) printed the address itself in public text. The row keeps the finding and says "the operator's personal email address"; a test fails if a document under `docs/`, README, SECURITY.md or the changelog prints a personal mailbox address.
- UI hardening (F-03 / #4, F-04 / #5): the page no longer embeds the API token. A one-time boot link (10 minutes, single use) sets an `HttpOnly; SameSite=Strict` session cookie and redirects; anyone else gets a static locked page. The UI script and CSS moved to separate files so the CSP can be `default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; frame-ancestors 'none'; form-action 'none'` with no `unsafe-inline` and no `unsafe-eval`. All HTML is now built with an escaping `html` tagged template and written only through `setHTML`, which refuses anything else; the 12 inline `style=` attributes became classes; event dispatch tables reject prototype keys.
  Evidence: the old UI was not exploitable against the real schema (every text value went through `esc()`, and the unescaped sites sit on numeric columns of STRICT tables, which reject text) so the audit's original rating of SEC-2 overstated it; it was a latent weakness. With every number in every API response replaced by an attack string (a schema that does not enforce types), the OLD UI injected elements on 5 of 7 tabs and the NEW UI passes all 41 browser-engine tests, including every view under type confusion.
- Web server hardening (F-04, #5): the editor refuses any peer that is not on this computer (a LAN peer sending `Host: localhost` used to get HTTP 200 and the API token; measured by the new test against the old code); `--addr` must be loopback (the `--allow-remote` option this step first had was removed, #58); busy default port falls back to a random loopback port; security headers on every response (`X-Frame-Options: DENY`, `frame-ancestors 'none'`, `nosniff`, `Referrer-Policy: no-referrer`, CORP); `/api/` requires `Content-Type: application/json` on state-changing requests and rejects cross-site `Origin`/`Sec-Fetch-Site`; constant-time token comparison; the server fails closed if the random source fails; read/write/idle timeouts; export filenames are sanitized. Not yet done from F-04: the token is still embedded in the page (bootstrap cookie + CSP script restrictions arrive with the UI step).
- Save decoder is bounded (F-03 / SEC-1, #4): the declared size is checked against a 256 MiB cap before decompression and the stream is read through a limit, so a ~65 KB hostile file no longer allocates ~165 MB. Tests: bomb with a lying header, over-cap header, over-cap file, truncation, size mismatch both ways, wrong flag, non-SQLite payload, round trip at real size, fuzz seeds.
- Layer 1 design audit (tracking issue #24): F-03 and F-04 (S0), F-05, F-07 and F-08 (S1), F-06 (pristine baseline and diff, #7) and the review pane (F-10, #11 slices) are delivered; the `foreign_keys` default stays off for ordinary edits (live test T4 is not run; the editor cascades deletes itself). The Layer 2 audits of 2026-10-07 and 2026-10-15 are in `docs/audit/`. (The review pane was later removed in #238; `docs/audit/2026-10-22-L2-findings-register.md` records what replaced it.)
- **The security scan runs the organisation's v2 shared workflow** (#355, audit findings CLD-3 and CLD-4): `security-scan` in `ci.yml` calls `reusable-security-scan-v2.yml` at a commit (Project-Arrakis/.github#9) instead of the old file. gitleaks now reads `.gitleaks.toml` and `.gitleaksignore` from the default branch, not from the pull request, so a pull request cannot weaken them (a change to either takes effect after it is merged); the token is `contents: read` and semgrep runs with `--metrics off`. The job and check names are unchanged. Still open: the semgrep rule sets are the live registry sets and the semgrep install has no hashes until the organisation's two maintainer-run jobs (rule snapshot, hash lock) have run and this job passes `tools-ref`.
- The security scan installs semgrep from a hash-locked requirements file and runs its rule sets from a committed snapshot, both pinned by the shared workflow commit (`tools-ref`), so neither can change under the build (audit CLD-3 and CLD-4).
- **Every connection that opens a save does not trust its schema** (#358, review R6 finding L3): `trusted_schema` was switched off on the working copy and its read handle only; the copy that the integrity check and Restore inspect (the current save and every backup chosen for Restore), the read-only open used by the diff, and the baseline copy of `WithBaseline` still had SQLite's default (on). They are switched off too, a test asks every one of them, and a guard test fails if shipped code opens a database file or a copy of a save without `trusted_schema(0)`.
- **Reads and the soundness check have a deadline, and a linked backups folder is refused** (#40, audit findings S7 and S8): a read of the working copy (the tabs, the Tables view, the exports) is stopped after 5 seconds, the list of tables ends with an error instead of holding the save's lock, and the soundness check of a decoded save (a backup chosen for Restore) is stopped after 60 seconds. A backups folder that is a link or a junction is refused before a backup is written, a backup is restored or old ones are removed, for the save and for the config files, as a linked save file already was.
